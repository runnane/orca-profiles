# AGENTS.md

Guidance for coding agents (and humans) working in this repo. Follows the
[agents.md](https://agents.md) convention.

## What this is

**Orca Profiles** — a read-only explorer for OrcaSlicer preset configs. It
answers what the slicer will not: which values did *you* change, why is this
file 359 keys long, and which of these presets does OrcaSlicer even load.

Two ways to run it: a container that reads a mounted config and serves the SPA
(the normal one), and a static build that reads a folder in the browser via the
File System Access API (Chromium-only, needs a desktop session).

## Setup

```bash
pnpm install
pnpm dev        # static mode, http://localhost:5173
pnpm gates      # ⭐ typecheck + lint + tests + build
pnpm report DIR # the same analysis in a terminal
pnpm deploy     # gates → rsync → build on the target → verify
```

Node ≥ 22, pnpm pinned by `packageManager`.

## Non-negotiable conventions

- **This repo is PUBLIC.** Nothing internal may ever be committed: no real
  OrcaSlicer config, no real preset or printer name, no LAN address, no
  hostname, no token. Use RFC 5737 (`192.0.2.x`) and `.invalid` in examples.
  Git history is permanent — a mistake here is not fixed by a later commit.
  `deploy.env` and `.mcp.json` are gitignored for exactly this reason.
- **The test fixture is generated, never copied.** `scripts/make-fixture.mjs`
  synthesises the *shapes* a real config has — detached copies, redundant
  overrides, two files claiming one name, an inactive profile, sync snapshots,
  credentials that are set — with invented names. `fixtures/` is gitignored and
  regenerated by `pnpm test`. A new behaviour needs a new shape in the
  generator, not a real config.
- **Behaviour is modelled on OrcaSlicer's own loader, and cited.** The four
  rules in the README each carry a v2.4.2 `Preset.cpp` / `PresetBundle.cpp` line
  reference. Before changing resolution, load order or profile handling, **read
  the source** — an earlier model built from reading config files alone produced
  five false "missing parent" findings. Cite what you check.
- **Credentials are stripped server-side, by key name.** Machine presets carry
  `printhost_apikey`, `printhost_password`, `print_host`; `OrcaSlicer.conf`
  carries `access_code`, `user_access_code`, `dev_sn` and a `local_machines` map
  **keyed by printer IP**. That conf gets an **allowlist** — three fields
  (`app.preset_folder`, `filaments`, `models`) — never a denylist, because a key
  that is itself the secret cannot be scrubbed by blanking values. Each field is
  **rebuilt from parsed values, never forwarded**, so a key sitting beside one of
  them inside its own object cannot ride along; and a section we could not read is
  **omitted rather than emitted empty**, because an empty `filaments` is the claim
  "nothing is installed" and the reader acts on it by hiding presets. Deciding by
  key name rather than by recognising a value is what keeps a credential we have
  never seen covered. See [`src/domain/redact.ts`](src/domain/redact.ts).
- **Test in the failing direction.** A check that cannot go red is not a check.
  The redaction tests use inputs that actually contain secrets, because the
  fixture's are blank and a test against it passed while the code leaked.
  `scripts/verify-deploy.mjs` is likewise checked against a deliberately leaky
  server.
- **Verify exposure from another machine.** A request made on the host answers
  over loopback whether or not the port is published, so it proves nothing. That
  is why `pnpm deploy` verifies from the deploying machine.
- **Never claim what the slicer does without knowing it.** Within one directory
  OrcaSlicer's load order is `directory_iterator` order, which is
  filesystem-dependent. Findings say the choice is arbitrary rather than naming
  a winner. Same rule anywhere else the source does not settle it.
- **The domain layer stays pure.** `src/domain/` has no I/O and no React: it
  takes `{path, text}[]` and returns data. That is what lets the same code run
  in the browser, in the container and in the terminal report. Readers live in
  `src/source/` (browser), `src/server/` (container) and
  `src/domain/load-fixtures.ts` (node/tests) — keep the three in agreement about
  what a config contains, including `OrcaSlicer.conf`. `scripts/build-sample.mjs`
  is a fourth producer of that payload and has to agree too: it bundles the
  fixture for the "load sample" path, conf included, through the *same*
  `redactConfJson` rather than a copy of it.
- **Branch → commit → PR, always from fresh `main`.** One issue → one PR → one
  merge. `--base main` explicitly. See
  the bundle's `pr-hygiene` skill.
- **Follow-ups become issues — never inline TODO text.** File them in the ORCA
  project with `issues_create_issue`, dedupe with a search first, and reference
  the key.
- **Comment on the issue when you start and when you finish.**

## Definition of done

`pnpm gates` green; `pnpm smoke` if you touched `src/ui/`; `pnpm test:server` if
you touched the server, Dockerfile or compose; no personal or internal data
committed; issue commented.

## Tracker

Issues live in the **ORCA** project in RCP (`issues_*` MCP tools). The repo is
on the PR-status webhook, so a branch or PR title containing the issue key moves
the issue automatically — draft → `IN_PROGRESS`, opened → `IN_REVIEW`, merged →
`MERGED`. **`tracksProduction` is on**: `MERGED` is not the end, `IN_PRODUCTION`
means the container on the target is actually serving the new code, which is
what `pnpm deploy` does.

The MCP connection needs `.mcp.json`, which is **not committed** (it names
internal infrastructure and this repo is public). Copy it from a sibling repo
locally; it reads `RESPAWN_MCP_TOKEN` from the environment.

## How agent instructions reach this repo

Ten repos run the same agent workflow against one tracker and one PR webhook.
They used to do it by copying `.claude/commands/` between each other, which
drifted measurably; RCP-878 replaced that with one bundle plus one manifest per
repo, and ORCA-31 adopted it here. There is nothing left to sync and no
`sha256sum` check to run.

- **The bundle** — `runnane/agent-userspace`: the constitution, the
  repo-agnostic workflow commands (`/fix`, `/auto`, `/plan`, `/research`,
  `/sweep`), and the `pr-hygiene`, `gate-failures` and `agent-isolation` skills.
- **[`.agents/repo.json`](.agents/repo.json)** — the facts that differ between
  repos: the gate command, `release`, `ci`, `liveBoundary`, `worktreeSafe`,
  `gatesDoc`. **A manifest field cannot be wrong the way copied prose can**,
  because the repo that owns the fact is the repo that writes it.
- **[`.agents/gates.md`](.agents/gates.md)** — this repo's gate particulars,
  including the two suites deliberately kept outside the gates.
- **What stays tracked here** — `CLAUDE.md`, this file and `.agents/`.

**The public-repo and generated-fixture rules are already stated above** and are
not repeated here — but note that this repo is the worked example the bundle's
constitution cites for *generate rather than sanitise*, so those two rules are
the ones a future edit must not quietly soften.

**An agent commits only in the repo it was invoked in.** A lesson for a sibling
is ported by filing a linked issue in that repo's project.
